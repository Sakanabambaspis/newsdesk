# Feature proposals — refreshing, summarizing & delivering digests better

**Date:** 2026-09-16 (overnight run) · **Status:** proposals only; no prototypes built.
**Anchor:** `docs/DESIGN.md` v0.1 and the shipped M0/M0.5 scaffold (see `docs/reviews/design-audit-20260916.md` for the audit these build on).

Six features, capped as instructed. Every one stays inside the v1 non-goals (§1.2): **no credentialed scraping, no opaque credibility scores, no multi-tenancy.** All are local-first, single-user, and reuse entities that already exist in the schema (watchlists, terms, source attachments, duplicate links, revisions, feedback).

---

## F1 — Per-watchlist digest runs (scoped scoring + diversity floor)

**Builds on:** the `Watchlist` / `WatchlistTerm` / `WatchlistSource` tables (§3.1); §1's "the product object is the watchlist"; §7's ranking-bias guard ("per-watchlist source quotas and diversity floors arrive with digests (M4)"); retires the audit's D7 debt (`WatchlistRepo.include_terms()` currently unions all watchlists).

**Shape:** `build_daily_digest(session, settings, watchlist_id=...)` scopes term matching to that watchlist's include/exclude terms, restricts candidates to sources attached via `watchlist_sources` (falling back to all sources when none attached), and applies a per-publisher cap (e.g. max 3 items per publisher per section) so high-volume feeds can't crowd out niche ones. The M0 keyword scorer (`normalize.relevance_score`) is reused unchanged — only its inputs get scoped.

**Why it doesn't violate §1.2:** ranking stays a transparent keyword-weight computation, shown per item with its matched terms; quotas are a stated mechanical rule, not a learned score. Single-user.

**Effort / milestone:** **M** · **M4** (this is the milestone that owns digests and per-watchlist scoping per `WatchlistRepo.include_terms()`'s own docstring).

## F2 — Digest outbox: file-first delivery with optional SMTP/webhook

**Builds on:** §4 stage 9 ("Outputs: log + watchlists → alerts, digests, exports; delivery failure retried, logged"); §13 M0 "local snapshots dir" pattern; §18's credential discipline (env/keyring, never stored or logged).

**Shape:** every built digest is written to `$NEWSDESK_HOME/outbox/<ts>-digest.md` (+ `.json`) unconditionally — the zero-config delivery path. Optional transports behind env config: `NEWSDESK_SMTP_HOST/USER/PASS/TO` sends the Markdown render as the mail body; `NEWSDESK_WEBHOOK_URL` POSTs the JSON. Each delivery attempt appends `digest_delivered` / `digest_delivery_failed` to the immutable log with the transport name and status — never the credentials — and the next scheduler tick (F6) retries failures.

**Why it doesn't violate §1.2:** this is *outbound* delivery to the user's own endpoints; it fetches nothing. SMTP credentials follow §18 rule 1 exactly (env/keyring per-run, actor-tagged log entries). File delivery needs no credentials at all.

**Effort / milestone:** **M** (S if only the file outbox ships first) · **M4**.

## F3 — Format-aware digest rendering (brief / detailed / timeline / comparison / raw)

**Builds on:** §1's watchlist property "Preferred output: brief summary, detailed report, timeline, comparison, raw source list"; §10's `summarize_cluster` format argument; §8's `changed_vs_earlier` field; the existing `render_markdown` (`pipeline/digest.py:166`) and per-item revisions (§12).

**Shape:** `render(digest, fmt=...)` dispatch table in `pipeline/digest.py`:
- **timeline** — items grouped by `published_at` buckets, revision counts annotated (pure Python over the existing digest dict; no new LLM calls);
- **comparison** — groups items sharing a `content_hash` / `duplicate_of` chain (already stored) side by side, so syndicated copies read as one story with N publishers;
- **detailed** — current briefing plus inline per-item summaries (what `--deep` does ad hoc in `cli.py:177-189`, promoted to a renderer);
- **raw** — the source list (id, publisher, url, hashes) for machine consumption;
- **brief** — the existing `render_markdown` output, kept as default.
The watchlist's preferred format is stored as a `WatchlistTerm`-style attribute or a column on `Watchlist` (§3.1 "Preferred output" made persistent).

**Why it doesn't violate §1.2:** all renderers are deterministic transformations of stored, provenance-bearing data; the comparison view explicitly *distinguishes syndication from independent confirmation* (§6), the opposite of an opaque score.

**Effort / milestone:** the **timeline** renderer is the **S** core · full set **M** · **M4**.

**Done check (S, timeline):** `newsdesk digest-daily --format timeline` prints items grouped by hour bucket with `rev N` markers, driven by a `render_timeline()` unit test over a fixture digest dict — no LLM configured.

## F4 — Transparent corroboration & freshness signals in digest ranking

**Builds on:** §7's signal table (Corroboration count — "independent publishers in cluster", M3; Freshness — "published_at vs retrieval lag", M4); §6's promise that hash-linked duplicates let the system count *independent publishers, not raw links*.

**Shape:** before LLM ranking, `_collect` computes two **separately stored, separately displayed** numbers per item:
- `corroboration`: count of *distinct publishers* across items sharing this item's `content_hash` chain (self + items whose `duplicate_of` resolves to it or vice versa) — the cheap tier-1 proxy for §6's cluster count until M2 clustering lands;
- `freshness_hours`: `now − (published_at or retrieved_at)` in hours.
Selection sorts by `(relevance desc, corroboration desc, freshness asc)` with the weights visible in the digest header (e.g. "ranked by relevance ×0.6, corroboration ×0.3, freshness ×0.1"), and both numbers appear on every item card.

**Why it doesn't violate §1.2:** this is the concrete implementation of §7's "signals stored separately; no single opaque score" — no blended credibility number exists, each factor is shown next to every item, and corroboration counts publishers, not source quality.

**Effort / milestone:** corroboration-from-duplicate-chains slice is **S** · full weighted selection **M** · **M2** (duplicate links exist today) with the weighted-selection refinement in **M4** alongside F1.

**Done check (S):** after `run_collection` on the two fixture feeds, the syndicated grid story's digest card shows `corroboration: 2` and the unique stories show `corroboration: 1` — asserted in a unit test over `build_daily_digest` output.

## F5 — Save / dismiss feedback steering the next digest

**Builds on:** §12 ("User corrections: saves/dismissals/… are `FeedbackEvent`s (M4) feeding ranking; they never mutate stored source data"); §14's north-star metric ("useful items per day — counted through explicit feedback").

**Shape:** `newsdesk save|dismiss <item_id> [--why text]` and `POST /feedback {item_id, verdict}` append `FeedbackEvent` rows and log `feedback_recorded`. Digest selection (F1's scoped collect) then applies mechanical, inspectable adjustments: items from publishers the user saved 2+ items of get a bounded rank bump; dismissed *terms* (extracted from dismissed items' matched watchlist terms) get a one-notch demotion, never silent exclusion. The digest footer shows the adjustment summary ("+3 items boosted by your saves, 1 term demoted") so the loop stays legible. This is also what makes §14's north-star metric computable.

**Why it doesn't violate §1.2:** explicit user feedback in a single-user local system is neither scraping nor a credibility score (it's *your* preference, applied to your ranking), and feedback rows are per-user by construction with no multi-user surface.

**Effort / milestone:** **M** · **M4** (its home milestone).

## F6 — Interval-driven collection with auto-digest (the scheduler)

**Builds on:** §15 M1 ("Scheduling (interval-driven collection)"); the already-shipped, still-unused `Source.fetch_interval_minutes` / `last_fetched_at` columns (§3.1, `models.py:41-44`); §4 stage 9's scheduled outputs; F2's outbox as the delivery target.

**Shape:** `newsdesk serve --loop` (and a bare `newsdesk cron` for systemd/timer setups): a loop that every N seconds selects enabled sources where `last_fetched_at is null or older than fetch_interval_minutes`, runs `run_collection(source_ids=...)` (per-source isolation already guarantees one bad source can't kill the pass), and after each pass whose window advanced builds the daily digest and writes it to the F2 outbox. `job_started`/`job_finished` log entries gain a `trigger: "scheduler" | "manual"` field so the immutable log answers "what ran when, and who asked".

**Why it doesn't violate §1.2:** it schedules the existing polite, robots-respecting fetchers; per-source intervals are honored per host via the existing rate limiter, and nothing about credentials or scoring changes.

**Effort / milestone:** **M** (the select-due-sources query + loop + trigger tagging; retry/backoff on repeatedly failing sources is the L follow-up) · **M1** (its milestone), delivering into F2's outbox in M4.

4. F6: long-running digest_item (vision/transcription) passes are deliberately excluded from the scheduler loop; confirm they should stay manual/MCP-only.
